# Smart Traffic Command & Intelligent Routing System

A professional Smart City traffic command center for monitoring, coordinating, and intelligently routing traffic across multiple planning authority jurisdictions.

## Problem Statement

Uneven distribution of traffic over planning authorities' jurisdictions leads to localized congestion, inefficient routing, delayed emergency response, and poor cross-authority coordination.

## Project Objective

Build an intelligent transportation system command center that:

- Monitors live traffic across jurisdictions in real time
- Balances traffic load between planning authorities
- Provides smart routing recommendations
- Coordinates emergency and ambulance priority corridors
- Integrates weather, signals, and analytics into a unified operations dashboard

## Current Phase

**Phase 13 — Advanced Traffic Analytics + Command Center**

This phase builds a command-center analytics layer on top of the traffic simulation state rather than inventing new numbers. The dashboard reads the current road, signal, weather, authority, prediction, and emergency data already generated by the app, then summarizes the live condition into KPIs, bottleneck rankings, authority imbalance indicators, root-cause insights, and decision support for operator review.

The page is intentionally simulation-only. It uses the existing front-end traffic model and generated state values to show what an operations dashboard could look like in a prototype environment. It does not claim live-sensor accuracy, external data feeds, or production telemetry.

## Phase 13 Advanced Traffic Analytics + Command Center

### Analytics architecture

- the analytics engine reads the live state from the shared traffic engine, the weather engine, the signal engine, authority coordination, prediction engine, and emergency module
- a bounded historical snapshot is maintained in the browser so the dashboard can compare current conditions against recent simulation points without building a large backend data store
- KPI cards derive values directly from active road utilization, speed, delay, signal efficiency, authority balance, weather impact, and emergency load
- bottleneck ranking uses the current road state and recent simulation pressure to identify the most congested corridors and their primary stressors
- root-cause summaries blend signal performance, weather impact, road pressure, and authority imbalance into an operational brief for the operator
- decision-support actions summarize the next likely intervention based on the present simulation state, while keeping all recommendations in the front-end demo layer

### Data sources used

- traffic engine: road utilization, density, average speed, delay, queue pressure, network totals
- signal engine: current mode, efficiency, average wait reduction, intersection summary
- weather engine: impact score, visibility, scenario label, alert conditions
- authority coordination engine: jurisdiction balance score, displacement risk, optimization plan
- prediction engine: risk road list, upcoming expected congestion, capacity breach indicators
- emergency engine: active priority incidents and active emergency status

### UI behavior

- the analytics page shows KPI cards for network health, speed, delay, bottlenecks, emergencies, and weather impact
- a trend chart compares recent utilization and speed snapshots over the live simulation window
- a bottleneck table ranks the most stressed corridors and highlights route status and delay metrics
- the authority section shows inter-jurisdiction pressure and cross-boundary risk, while the signal section summarizes the current mode and efficiency
- an activity feed mirrors recent signal and authority events to support command-center monitoring
- an export button generates a CSV snapshot of the current simulated road state for operator review

### Operational limits

- no live sensor or public traffic feed is connected
- no backend analytics warehouse is created for production-grade reporting
- no real-world dispatch, authority API, or predictive model is implemented beyond the simulated traffic layer
- all analytics are derived from the project’s simulated state and intended for front-end operational demonstration only

## Phase 12 Multi-Authority Coordination Model

### Authority imbalance detection

- each road is mapped to its planning authority using the existing base traffic model
- total load, average utilization, queue pressure, and cross-boundary flow are aggregated per authority
- the dashboard computes a jurisdiction spread between overloaded and underloaded authorities
- the system warns when traffic displacement is detected across nearby planning boundaries

### Coordination logic

- overloaded authorities trigger a recommended reduction in queue pressure by shifting selective inbound or outbound load to adjacent low-pressure corridors
- underloaded authorities are identified as potential balancing targets based on lower utilization and cross-jurisdiction connection density
- the optimization plan compares before and after simulated utilization levels to estimate network improvement
- the coordination engine keeps all recommendation logic in the front-end simulation layer and does not issue live field action

### UI behavior

- the authorities page shows network balance score, displacement risk, optimization gain, and current scenario summary
- the dashboard lists each authority's load, speed, queue, cross-boundary flow, and status
- the optimization panel proposes corridor-balancing actions for overloaded zones, with a live scenario summary and event log
- the page clearly displays SIMULATED MULTI-AUTHORITY SYSTEM and warns that this is a demo-only coordination mode

### Operational limits

- no real authority APIs or jurisdiction data feeds are connected
- no live signal control or traffic diversion is executed
- no backend data orchestration or production dispatch logic is present
- all coordination and balancing are front-end simulation logic only

## Phase 11 Smart Ambulance Finder Model

### Recommendation engine

- each unit is scored by ETA, distance, price, rating, and current route pressure
- the recommendation engine ranks units by recommended score, then by fastest, nearest, or cheapest, depending on the selected sort mode
- the model uses a lightweight cost approach with free simulated pricing rather than a paid service or external dispatch API

### Pricing and distance model

- each ambulance has a simulated base price, service tier, and dispatch profile
- route cost blends travel distance, urgency surcharge, weather penalty, and traffic delay multiplier
- the final recommendation panel shows estimated arrival time, total route distance, price, and current unit availability

### Integration with previous phases

## Phase 10 Weather-Aware Traffic Intelligence Model

### Weather impact architecture

- weather scenarios are defined as lightweight profiles such as clear, light rain, heavy rain, fog, and storm
- each profile includes temperature, humidity, wind, visibility, speed reduction, and capacity reduction
- the weather engine computes effective road speed and capacity as derived metrics, keeping the original road definitions intact
- the same weather state is reused by routing, prediction, signal optimization, and emergency prioritization logic

### Traffic, routing, prediction, and signal integration

- road utilization and network delay are adjusted by weather impact multipliers without modifying permanent base values
- routing cost penalties increase as visibility drops and rain severity rises, which changes recommended corridor options
- prediction engine snapshots keep weather impact metadata so forecasts reflect adverse conditions without breaking the prior model
- signal logic applies weather-related delay and efficiency adjustments to demand and average wait calculations
- emergency route planning uses the same weather-aware cost model, so green-corridor requests and ETA estimates reflect degraded conditions

### UI behavior

- the weather page provides a scenario selector with clear, light rain, heavy rain, fog, and storm states
- the dashboard shows the active weather condition, visibility, network impact, hotspot count, and historical scenario changes
- the UI is clearly labeled as SIMULATED WEATHER MODE and does not imply live environmental accuracy
- no real weather API key or paid provider is required

### Operational limits

- no live external weather service is queried
- no real-world sensor data or traffic feed is required
- all weather behavior is a front-end simulation for planning and demonstration only

## Phase 9 Emergency Control Model

The emergency coordination system is intentionally transparent and prototype-focused. It builds on the existing routing and signal stacks rather than introducing a separate traffic control architecture.

### Emergency vehicle priority logic

- each emergency vehicle is modeled as a simulated route from origin to destination using the existing road graph
- vehicle priority is derived from vehicle type and requested emergency classification
- critical and high-priority vehicles receive a preemption request in advance of the next critical junction
- green-corridor activation is simulated as a temporary emergency signal mode, without actual live signal control

### Signal preemption and green corridor

- the emergency engine evaluates the next major intersection on the route and requests priority access
- a queued request is granted when the intersection is available without conflicting with another active emergency corridor
- the signal dashboard switches into emergency priority mode for the active route, representing a temporary green corridor
- the event log records request, approval, and restoration of normal operation

### Live LED and alert display

- alert cards show normal, warning, critical, and restoration states based on vehicle progress and priority level
- the LED panel summarizes the active emergency vehicle, current route, ETA, and corridor condition
- the command center displays route and signal information in a simulation-safe readout for operator review

### Routing and ETA integration

- emergency routes reuse the existing route network and road metadata from the smart routing logic
- ETA is predicted from current road distance, priority weighting, and the simulated progress of the emergency vehicle
- the dashboard compares the route in real time and presents a time-saved estimate against the baseline corridor travel plan

### Operational limits

- no backend dispatch or real authority integration exists in this prototype
- no live sensor data, radio telemetry, or CAD system is connected
- the system is designed as a front-end simulation and demonstration tool only

This phase is intentionally limited to the command-center simulation layer and does not extend into a real-world intervention system.

## Phase 8 Signal Control Model

The signal control system is intentionally transparent and rule-based. It does not claim to be AI-controlled or real-world signal automation. Instead, it uses the existing traffic simulation state to evaluate density and queue pressure at each intersection and recommend smart green-time allocation with minimum and maximum fairness constraints.

### Signal architecture

- intersection model stores the core signal state, cycle settings, phase data, connected roads, and approach metrics
- approach model computes vehicle count, queue length, utilization, speed, arrival rate, departure rate, waiting time, and density per direction
- demand score blends normalized density, queue, arrival rate, and waiting time into a single signal demand value
- green time calculation awards more green to the higher-demand axis while enforcing minimum and maximum green constraints
- fairness logic prevents starvation by keeping a minimum green window for lower-demand directions
- fixed signal mode provides a baseline timing plan for comparison against the smart signal model
- the before/after comparison calculates simulated waiting-time and queue reduction from baseline versus optimized operating conditions

### Demand score and green-time calculation

- demandScore = densityWeight × density + queueWeight × queue + arrivalWeight × arrival + waitingWeight × waiting
- normalized values are constrained to a 0 to 1 range before being combined
- recommended green time = minimumGreen + (demandScore × (maximumGreen - minimumGreen))
- green time never drops below minimumGreenTime and never exceeds maximumGreenTime
- cycle length remains configurable and the total phase structure remains consistent with the signal plan

### Queue and waiting time model

- when an approach is red, incoming vehicles are accumulated into queue length
- when an approach is green, discharge rate follows the connected road capacity, signal mode, and road utilization
- waiting time combines queue length, red duration pressure, and arrival load
- average wait and average queue are derived from all approach values at the monitored intersection

### Before/after comparison

The system computes a fixed-signal baseline versus smart-signal optimized output using formulas such as:

- reduction = ((baseline - optimized) / baseline) × 100
- when baseline values are zero, the system safely falls back to 0 instead of dividing by zero

This is a simulation-only comparison and is displayed as a prototype metric, not as verified field performance.

### Prediction and routing integration

The signal engine is aware of the existing simulation state and supports forecast-aware operation. If a corridor is projected to become congested, the recommendation panel notes the upcoming demand. Routing is also referenced as an informational alternative route when a signal is severely congested, but no automatic redirection is forced.

This is a simulation-based signal optimization prototype. It does not control real-world traffic signals.

## Backend Setup

1. Open a terminal in the project root.
2. Navigate to the backend folder:

```bash
cd backend
```

3. Copy the example environment file:

```bash
copy .env.example .env
```

4. Update the values in `.env` with local database and secret settings.

5. Install dependencies when Node.js is available:

```bash
npm install
```

6. Generate Prisma client:

```bash
npm run prisma:generate
```

7. Create the database and run migration:

```bash
npm run prisma:migrate
```

8. Start the backend:

```bash
npm run dev
```

## Database Setup

PostgreSQL must be running locally. Example local configuration:

```text
postgresql://postgres:postgres@localhost:5432/flowx_traffic?schema=public
```

Update `DATABASE_URL` in `backend/.env` to match your local server. The schema includes the `User` model with roles and auth provider support.

## Authentication Flow

- User signs up from the existing FlowX auth page.
- Frontend calls the backend signup endpoint.
- Password is hashed with bcrypt.
- JWT token is issued and stored in the browser session for the prototype flow.
- Dashboard checks token presence and redirects unauthenticated users to the login screen.
- The backend validates JWTs via middleware on protected routes.

## How to Run Locally

No build step or dependencies are required.

### Option 1 — Open directly

1. Navigate to the project folder.
2. Open `index.html` in a modern browser (Chrome, Firefox, Edge, Safari).
3. You will be redirected to `pages/dashboard.html`.

### Option 2 — Local HTTP server (recommended)

Using Python:

```bash
cd smart-traffic-command-center
python -m http.server 8080
```

Then open [http://localhost:8080](http://localhost:8080) in your browser.

Using Node.js (if installed):

```bash
npx serve .
```

Using VS Code / Cursor Live Server extension:

1. Open the project folder.
2. Right-click `index.html` → **Open with Live Server**.
